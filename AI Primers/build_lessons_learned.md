# Build Lessons Learned — CuraFeather Session (June 2026)

> Supplements `CuraEngine_Local_Fork_Build_Guide.md` with hard-won findings from actually building CuraFeather (a 5.14-alpha fork) against Cura 5.13 on Windows 10 / VS2026 / MSVC 195.

---

## 1. VS Developer Environment Must Be Initialised Before Conan/CMake

Conan's `conan install` and `cmake --preset conan-release` both require MSVC tools on PATH. They do **not** self-initialise. You must call `VsDevCmd.bat -arch=amd64` first in the same shell session.

- Path on VS 2026 Community: `C:\Program Files\Microsoft Visual Studio\18\Community\Common7\Tools\VsDevCmd.bat`
- In a `.bat` file, use `call` — not `start` or `&`:
  ```bat
  call "C:\Program Files\Microsoft Visual Studio\18\Community\Common7\Tools\VsDevCmd.bat" -arch=amd64
  ```
- `VsDevCmd.bat` bypasses stdout redirects when invoked from a batch file. Put your `>> log.txt 2>&1` redirects **after** the `call` line, not on it.
- `vswhere.exe` is not on PATH by default in an elevated window — use the full path or initialise with `VsDevCmd.bat` first.

---

## 2. Build Commands — Exact Sequence

```bat
call "C:\...\VsDevCmd.bat" -arch=amd64
cd /d C:\Users\ricsz\source\repos\CuraFeather
conan install . --build=missing -s build_type=Release
cmake --preset conan-release
cmake --build --preset conan-release
```

- The CMake preset name is `conan-release` (generated by Conan into `CMakeUserPresets.json`). Do not use `--config Release` — the preset bakes it in.
- Ninja (used by the preset) resumes from completed object files if the build is interrupted — you do not need to start from scratch after a cancelled build.

## 3. Arcus Must Be Built as a Static Library

CuraEngine links against `arcus`. Cura's install directory also ships an `Arcus.dll` for its Python frontend (`pyArcus.pyd`). If you build Arcus as shared (the default), Windows loads Cura's `Arcus.dll` into your engine process, causing `0xC0000005 STATUS_ACCESS_VIOLATION` in `Arcus.dll` at startup.

**Fix in `conanfile.py`:**
```python
def configure(self):
    super().configure()
    if self.options.enable_arcus:
        self.options["arcus"].shared = False  # bake Arcus into CuraEngine.exe
```

With static Arcus, the resulting `CuraEngine.exe` is ~10 MB and has no `Arcus.dll` in its import table. Confirmed via `dumpbin /IMPORTS`.

---

## 4. Do Not Replace Arcus.dll or polyclipping.dll

These two DLLs are in Cura's install directory and are imported by `pyArcus.pyd` (Cura's Python binding). Replacing them with your build's versions causes:

```
ImportError: DLL load failed while importing pyArcus: The specified procedure could not be found.
```

Cura's Python frontend then fails to start. Leave both files untouched — the static Arcus fix eliminates the need to replace `Arcus.dll` anyway.

---

## 5. Engine–Frontend Protocol Version Lock

CuraEngine communicates with the Cura frontend via protobuf messages defined in `curaengine_grpc_definitions`. The version of this package must match between engine and frontend:

| Cura Version | `curaengine_grpc_definitions` |
|---|---|
| 5.13 | 0.4.0 |
| 5.14 | 0.4.1 |

Running a 5.14 engine against a 5.13 frontend: the engine slices successfully (exit code 0) but Cura logs `UnknownMessageTypeError` on the Arcus socket and shows no layers. The G-code is never received. **The engine version must match the frontend version.**

---

## 6. Settings Schema Must Also Match

CuraEngine reads named settings passed by the frontend via protobuf. Any setting the engine calls `settings.get<T>("name")` on that was not sent by the frontend causes:

```
[error] Trying to retrieve setting with no value given: <setting_name>
```

followed by exit code 2 (controlled abort) or `0xC0000409 STATUS_STACK_BUFFER_OVERRUN` if the garbage read is used as a pointer/size.

Settings added in 5.14 that are absent from Cura 5.13's `fdmprinter.def.json`:

| Setting | Type | Safe default |
|---|---|---|
| `top_bottom_skin_merge_distance` | float (mm) | `0` |
| `minimum_infill_line_length` | float (mm) | `0` |
| `material_density` | float (g/cm³) | `1.24` |

These were patched into `packaging/fdmprinter.def.json`. However, the protocol mismatch (§5) renders this moot — it is listed here for completeness and to explain the one-by-one error sequence if you repeat this experiment.

---

## 7. Attempting a 5.13 CuraEngine Build Fails on Protobuf

When we attempted to build the CuraEngine 5.13 branch (to eliminate the 5.14/5.13 frontend mismatch), Conan resolved a conflict:

- `curaengine_grpc_definitions/0.4.0` required `protobuf/6.33.5`
- Cached `grpc/1.78.1` required `protobuf/3.21.12`

These are mutually exclusive. Resolution requires either cleaning the Conan cache or pinning the protobuf version. This build was abandoned during the session.

## 8. Build Output Size as a Sanity Check

| Build | `CuraEngine.exe` size | Notes |
|---|---|---|
| 5.14 shared Arcus | ~8 MB | Arcus.dll required alongside |
| 5.14 static Arcus | ~10.1 MB | No Arcus.dll needed, correct |

A sudden size regression after a conan/cmake change is a sign the static link was lost.

---

## 9. Confirmed DLL Dependency Chain (5.14 static Arcus build)

From `dumpbin /IMPORTS CuraEngine.exe`:

- `polyclipping.dll` — load from Cura's directory; Cura's copy imports only MSVC CRT (safe)
- `cura-formulae-engine.dll` — must deploy ours (5.14 requires v1.1.0; Cura 5.13 ships older)
- `tbb12.dll`, `tbbbind_2_5.dll`, `tbbmalloc.dll`, `tbbmalloc_proxy.dll` — deploy ours
- `MSVCP140.dll`, `VCRUNTIME140.dll` — Windows/VS redistributable, always present

`cura-formulae-engine.dll` imports only MSVC CRT — no Arcus chain through it.

---

## 10. Conclusion for Next Session

The correct approach is to build **CuraEngine 5.13** (matching Cura 5.13's frontend). This eliminates:
- Settings schema mismatches
- Protocol version mismatches  
- The Arcus DLL conflict (may resolve naturally without static-link workaround)

The static Arcus change in `conanfile.py` should still be applied as a precaution until the Arcus ABI match is confirmed.
